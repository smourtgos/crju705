Lab 6 · Joining Data

CRJU 705 · Session 6

Goal: combine two datasets into one — correctly — and learn to spot the ways joins quietly go wrong. This lab assumes you’ve read R4DS Ch. 19 (Joins) and skimmed Ch. 18 (Missing values).

How labs work: run the Setup chunk as-is, follow the Walkthrough along with me, then complete the Your Turn tasks in your own script. The Exit Ticket gets submitted to Canvas before you leave.

Walkthrough

A question neither file can answer alone

Do incidents in lower-income community areas end in arrest at a different rate than incidents in higher-income areas?

Look at what that question needs: arrest lives in crimes (one row per incident), and median_income lives in areas (one row per community area). No single file has both. This is the everyday reality of CJ data — incidents in one system, census context in another, personnel records in a third. Joins are how you put them together.

Keys first, join second

A join matches rows using a key. Before joining anything, identify:

  • the primary key — the column(s) that uniquely identify each row of one table
  • the foreign key — the matching column in the other table

community_area should be the primary key of areas: one row per area. Never assume — check:

areas |> count(community_area) |> filter(n > 1)
# A tibble: 0 × 2
# ℹ 2 variables: community_area <dbl>, n <int>

Zero rows means no duplicates — community_area really does uniquely identify each of the 77 areas. In crimes, community_area is a foreign key: thousands of incidents point to each area. That’s a many-to-one join — many incidents, one area each.

left_join() — and a trap on the very first try

joined_naive <- crimes |> left_join(areas, by = "community_area")

joined_naive |> select(id, community.x, community.y) |> head(3)
# A tibble: 3 × 3
        id community.x    community.y   
     <dbl> <chr>          <chr>         
1    28545 Roseland       Roseland      
2    28546 South Lawndale South Lawndale
3 13707861 Belmont Cragin Belmont Cragin

Where did community.x and community.y come from? Both tables have a column named community, and it wasn’t part of the key — so R kept both copies and slapped suffixes on them. Harmless here (they agree), but confusing, and with messier data the two versions might not agree.

The cleaner habit: select just the columns you need from the right-hand table before joining.

joined <- crimes |>
  left_join(
    areas |> select(community_area, median_income, unemployment_rate),
    by = "community_area"
  )

joined |> select(id, community, arrest, median_income) |> head(3)
# A tibble: 3 × 4
        id community      arrest median_income
     <dbl> <chr>          <lgl>          <dbl>
1    28545 Roseland       FALSE          48745
2    28546 South Lawndale TRUE           54569
3 13707861 Belmont Cragin FALSE          68284

Row-count discipline

A many-to-one join should return exactly the rows of the left table, just wider. Verify it every time:

nrow(crimes)
[1] 30000
nrow(joined)
[1] 30000

If the joined table had grown, that would mean the “one” side secretly had duplicate keys — every duplicate multiplies your rows and silently corrupts every count and mean downstream. nrow() before and after is a two-second insurance policy.

Now answer the question

Split areas at the median of median_income and compare arrest rates:

joined |>
  mutate(income_group = if_else(median_income < median(areas$median_income),
                                "Lower-income area", "Higher-income area")) |>
  summarize(arrest_rate = mean(arrest), n = n(), .by = income_group)
# A tibble: 2 × 3
  income_group       arrest_rate     n
  <chr>                    <dbl> <int>
1 Lower-income area        0.183 16326
2 Higher-income area       0.134 13674

Incidents in lower-income areas end in arrest about 18% of the time, versus about 13% in higher-income areas — a gap we could not have computed from either file alone.

Interpret with care. This is an area-level pattern attached to incidents. It does not tell us why — the mix of offense types differs across areas, police deployment differs, reporting differs. And median_income describes the area, not the people involved in any incident. Joins expand what you can ask; they don’t excuse you from thinking about what the answer means.

When keys don’t match: a small disaster on purpose

Our Chicago files join perfectly, which is lovely and completely unrepresentative of real life. Here’s a tiny example with the kind of flaws you’ll actually meet — a table of incidents and a lookup table of district commanders:

incidents_toy <- tribble(
  ~incident_id, ~district,
  101, "Central",
  102, "Central",
  103, "Harrison",
  104, "Shakespeare"
)

district_info <- tribble(
  ~district,    ~commander,
  "Central",    "Diaz",
  "Harrison",   "Okafor",
  "Town Hall",  "Reyes"
)

Incident 104 is in a district the lookup table doesn’t know; Town Hall has a commander but no incidents. Watch what each join does with the mismatches:

incidents_toy |> left_join(district_info, by = "district")
# A tibble: 4 × 3
  incident_id district    commander
        <dbl> <chr>       <chr>    
1         101 Central     Diaz     
2         102 Central     Diaz     
3         103 Harrison    Okafor   
4         104 Shakespeare <NA>

left_join() keeps every left-hand row and fills the holes with NA — incident 104 survives, commander unknown.

incidents_toy |> inner_join(district_info, by = "district")
# A tibble: 3 × 3
  incident_id district commander
        <dbl> <chr>    <chr>    
1         101 Central  Diaz     
2         102 Central  Diaz     
3         103 Harrison Okafor

inner_join() keeps only rows that match — incident 104 is silently gone. Four incidents in, three out, no warning. If you didn’t check row counts, you’d never know you dropped data.

anti_join() — find the orphans before you commit

anti_join() returns the left-hand rows that have no match — it’s the diagnostic you run before choosing a join:

incidents_toy |> anti_join(district_info, by = "district")   # incidents with no district info
# A tibble: 1 × 2
  incident_id district   
        <dbl> <chr>      
1         104 Shakespeare
district_info |> anti_join(incidents_toy, by = "district")   # districts with no incidents
# A tibble: 1 × 2
  district  commander
  <chr>     <chr>    
1 Town Hall Reyes

Run it both directions on our real files:

crimes |> anti_join(areas, by = "community_area") |> nrow()
[1] 0
areas  |> anti_join(crimes, by = "community_area") |> nrow()
[1] 0

Zero and zero: every incident matches an area, every area has incidents. Our keys are clean — and the only reason we know that is that we checked.

The missing-values moment (the Ch. 18 skim, cashed in)

That NA commander left_join() created is a genuine missing value, and NAs are contagious by design:

toy_joined <- incidents_toy |> left_join(district_info, by = "district")

toy_joined |> filter(is.na(commander))   # locate the missing
# A tibble: 1 × 3
  incident_id district    commander
        <dbl> <chr>       <chr>    
1         104 Shakespeare <NA>

The same discipline applies to missingness that arrives with the data. Our crime file has incidents with no coordinates (blocked addresses, data-entry gaps):

sum(is.na(crimes$latitude))
[1] 190
mean(crimes$latitude)
[1] NA
mean(crimes$latitude, na.rm = TRUE)
[1] 41.84574

One missing value poisons the whole mean until you decide — explicitly — what to do about it. na.rm = TRUE is a decision (“compute on the cases we have”), not a reflex. The worst option is not noticing the NAs exist; that’s what sum(is.na(...)) is for.
